## 环境与样本

- MacBookAir10,1，Apple M1，8 逻辑 CPU，8 GiB 内存；macOS 15.6.1 arm64，Python 3.11.4。硬件信息由实际 `sysctl` 读取。没有独占整台主机，不把结果视为实验室无干扰极限值。
- 每次新建专属临时数据库，退出后仅回收自己的 TemporaryDirectory；不读取旧性能库和真实研究数据。不启动采集，不访问上游网络，实际本地 HTTP `127.0.0.1:8874`。端口已占用时失败，不停止别人的实例。
- 10 个议题、20,000 条材料、2,500 条说法、2,500 条事件、10 条判断、1 个来源，共 25,021 个记录及版本。材料均有明显夹具标记，摘录/译文为空，采集时间为本轮生成时间；无 activity change、无额外历史版本、无附件。这是 PRD 容量下相对轻的元数据工作负载，不代表多年历史容量。
- 每个议题含 2,000 条材料、250 条说法、250 条事件。5 个会话读取 5 个不同议题。筛选响应 50 条/总数 2,000；搜索响应 50 条/总数 1,000；bundle 返回完整 2,000 条材料及研究记录。
- 三种接口分别先做 1 轮 5 并发预热，再做 8 轮 5 并发，共每类 **40 个正式样本**，共 120 个正式样本及 15 次预热。P95 使用排序后第 `ceil(0.95×40)=38` 个值。每轮使用 Barrier 同时发出 5 个真实 GET；每次新建 HTTP 连接；收到正文后停止客户端计时，待该轮 5 个响应全部收到才解析 JSON、核对条数。
- SQLite/操作系统为生成夹具后的热缓存；各类一次预热不计入。记录实际同进程 HTTP 处理，非 direct dispatch 微基准。生成耗时 0.805 秒，全流程 133.871 秒。

## 瓶颈和建议

已观察到的瓶颈是全库权限输入和事务串行化：权限上下文占持锁时间的 91.3% / 81.7% / 83.5%；其中快照仅占上下文的 21.0% / 22.8% / 22.6%，其余包括全库历史索引、候选到期评估和权限事实构造。事务等待占 dispatch 的约 66.6%–67.6%。一次请求的全库工作会延迟另外四个读取会话。把同一 full snapshots SQL 加速无法消除约 0.64 秒/请求的其余全库处理，也无法单独解决排队。

建议 root 增加公开 `Store.policy_snapshots(evidence_ids)` 或等价有界策略读取接口，在同一事务中按目标材料提取必要版本。实现至少保留：

1. 目标材料全部历史，包括已移除的来源/渠道和历史 original 关系；递归原始出处的全部版本，不能只读取当前来源。
2. 涉及来源全部政策历史和恢复时保留的 `recovery_source_policy` 事实；材料不可变首次保存/采集时间、当前及历史 content_expired 标记。
3. 保留设置，以及决定候选是否受保护的当前/历史研究引用和人工操作事实。建议平台以引用索引找相关历史依赖，而非扫描所有研究正文。不能漏掉旧判断版本、路径边和已解除关联后的历史引用。
4. 对一般分页/筛选先确定目标材料 ID，再读取权限输入；search 必须在授权净化后决定正文匹配与总数，不能用受限摘录做查询后泄露匹配事实。可先缩小议题/元数据候选，针对这些候选取策略。bundle 的集合还须包含固定版本引用和跨议题材料。

以上是基于计时和代码路径的优化建议，并非已实现的性能保证。不得靠跨请求不失效缓存、跳过历史或放宽读取权限换取通过。root 独占后续 Store/领域优化。
